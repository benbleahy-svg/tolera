Database — PostgreSQL 16 + pgvector

Self-hosted on Hetzner. Do not use a managed PostgreSQL service for v1.

Why not managed (Supabase, Neon, RDS)?

OptionProblem
Hetzner Managed DBDoes not support the pgvector extension — a hard requirement for geometry similarity search and AI embeddings. Not viable.
Supabase EUpgvector ✓, EU region ✓, but adds US-company GDPR complexity, extra subprocessor, and a REST/realtime layer you don't need. Adds cost and abstraction over pure Postgres.
Neon EUServerless Postgres — great for dev branching, but production reliability at manufacturing workloads (large STEP file ingests, geometry queries) is unproven for this use case.
AWS RDS EUExpensive (3–5× Hetzner cost), US-company DPA complexity, overkill.

Recommendation: Self-hosted PostgreSQL 16 on Hetzner CX32/CX42. Install pgvector from source (pgvector v0.7+ supports HNSW indexing — use this over IVFFlat for geometry similarity). Automated pg_dump to Hetzner Object Storage nightly + WAL archiving for point-in-time recovery.

Key PostgreSQL configuration for this workload

SettingValue (CX32 8GB)Why
shared_buffers2GB25% of RAM — standard
work_mem64MBGeometry/vector queries need working memory
maintenance_work_mem512MBHNSW index builds are memory-intensive
max_connections100Use PgBouncer in front; DB should not see raw app connections at SaaS scale
wal_levelreplicaRequired for streaming replication (SaaS)
pgvector hnsw.ef_construction128Higher accuracy for geometry similarity at build time
PgBouncer: Add PgBouncer connection pooling from day one, even on the pilot. FastAPI + Celery will open many short-lived connections. PgBouncer in transaction mode keeps the DB connection count manageable. Run it as a sidecar on the DB server.

Redis — Cache, Celery broker, undo TTLs

Redis is used for: Celery task broker + result backend; org AI settings cache (5-min TTL); quote assembly undo keys (60s TTL); session caching; rate limiting.

Pilot: self-hosted on app-01

Redis in a Docker container on the app server. No persistence needed for the queue (if Redis restarts, in-flight Celery tasks are lost but re-queued on next trigger). Enable AOF persistence for the AI settings cache. Cost: €0 (included in app server).

SaaS: Upstash EU Frankfurt

Upstash is serverless Redis, billed per request. EU Frankfurt region is GDPR-compliant with DPA available. Pay-as-you-go: $0.2 per 100k requests. For 5–20 orgs, expect $10–30/month. No server to manage, automatic failover.

Alternative: self-hosted Redis Sentinel (3-node HA) on Hetzner CX22s. More work to operate, ~€12/month for the instances. Upstash is simpler for a solo dev.

Do not store file content or PII in Redis. The 60s undo keys store only a line_item_id reference — not the router data itself (that stays in Postgres). The AI settings cache stores toggles, not customer data.

File retention for GoBD compliance: Quote PDFs are legal commercial documents requiring 10-year retention. Never allow deletion of sent-quote PDFs even via admin tooling — see build spec § GDPR erasure decision (DB anonymization only; files kept).

Auth — Clerk

Clerk handles the full authentication lifecycle (login, sessions, org management, invite flows, SSO/SAML). Already decided in the build spec. Key infrastructure notes:

Critical: use the EU Clerk instance

Clerk has a separate EU instance (clerk.com → eu.clerk.com) that stores all identity data in the EU. You must use this from day one. It is not trivially migrated later. Create your Clerk app in the EU instance — the Frontend API domain will be *.clerk.accounts.dev routing through EU infrastructure.

PlanPriceWhat you need it for
Free€0Up to 10k MAU, all core auth (email, passkeys, Google/Microsoft). Fine for pilot.
Pro$25/moCustom email domain (quotes sent from @yourdomain.com not @clerk.com), custom SMS, advanced rate limiting. Needed before SaaS launch.
EnterpriseCustomSAML SSO for enterprise customers, custom DPA. Needed when you land a customer requiring SSO.
Org model: Use Clerk's native Organizations — each shop is one Clerk org. Roles (Admin, Estimator, etc.) are stored in BF's own user_org_roles table and mirrored via Clerk webhooks. Do not rely on Clerk roles for authorization — BF's Postgres is the source of truth for permissions.

Email — Mailgun EU

Mailgun handles both directions: inbound (RFQ emails forwarded to {org-slug}@rfq.bidfactory.app → webhook → auto-quote creation) and outbound (quote send, notifications, order confirmations).

Critical: use Mailgun's EU region

Mailgun has a US region and an EU region. The EU region API endpoint is api.eu.mailgun.net. All email data (content, recipients, attachments) stored in EU. Set this from day one — domains are region-locked and cannot be migrated.

PlanPriceWhen
FlexFree (100 emails/day), then $0.001/emailPilot. A shop sending 20 quotes/day with ~3 recipients each = 60 emails/day. Likely free or pennies.
Foundation~€35/month for 50k emailsSaaS with 10+ orgs. 10 orgs × 200 emails/month = 2k emails — actually still cheap on Flex. Move to Foundation when you need dedicated IPs for deliverability.

Inbound routing setup

Configure a Mailgun route that matches .*@rfq.bidfactory.app, forwards the parsed email (subject, body, attachments) via webhook to POST /ingest/email. Mailgun parses MIME, extracts attachments, and posts them as multipart form data. The FastAPI endpoint validates the Mailgun signature, saves attachments to Object Storage, and enqueues the Wingman parse job. Add MX records for rfq.bidfactory.app pointing to Mailgun.

Attachment size limit: Mailgun's inbound webhook supports up to 25MB per attachment (email server limit). The build spec's 200MB file size limit applies to direct uploads (Smart RFQ form, Part Viewer upload), not email ingest. Document this distinction — customers with large assemblies should use the Smart RFQ form, not email forwarding.

GDPR — the critical step

Anthropic is a US company. Drawing content (technical PDFs, STEP file text) is sent to the Claude API during Wingman extraction. Before sending any customer files to the API, you must:

  1. Sign Anthropic's Data Processing Addendum (DPA) — request from Anthropic enterprise sales or find via the API console
  2. Confirm zero-data-retention agreement is in the DPA (Anthropic offers this for API customers — they do not train on API data)
  3. Add Anthropic as a named subprocessor in your customer DPA / Privacy Policy with a description of what data is processed and the legal basis
  4. Enforce the AI processing toggle — when disabled, no data leaves the EU environment
  5. Enforce the CUI/ITAR auto-skip — flagged files never go to the API regardless of toggle state
This is not optional before you sign a DACH customer. German manufacturing shops will ask for your subprocessor list in their supplier qualification process. Have the DPA in hand before the first pilot.

Prompt + eval management

Store all prompts under extraction/prompts/ in the repo (version-controlled). Store eval fixtures under extraction/evals/. Run the eval suite on every PR that touches a prompt file — this is how you catch regressions before they reach production. Use pytest + a small harness that calls the Claude API against fixture drawings and checks accuracy against known-good outputs.

Background Workers — Celery queues

Celery + Redis broker handles all async work. Do not run all task types on the same worker pool — geometry/nesting is CPU-bound and will starve I/O-bound tasks (AI calls, email sends) if they share workers.

Celery Beat (scheduled tasks)

Celery Beat handles periodic tasks: nightly rule-suggestion pattern scan, daily backup verification ping, nightly pg_dump trigger, daily Margin Coach benchmark cache rebuild. Run Beat on the app server as a separate process (one instance only — not replicated).

PDF Generation — WeasyPrint

Quote PDFs (generated at send time and stored in Object Storage) require HTML-to-PDF with full CSS support for branding, tables, and multi-page layout. WeasyPrint (Python library, no external service) is the right choice.

OptionVerdict
WeasyPrint✓ Recommended. Pure Python, good CSS support, handles paged media (page breaks, headers/footers, page numbers), EU-safe (no external calls), already used in many Django/FastAPI stacks.
ReportLabProgrammatic PDF (draw every element in code). Too low-level for a templated quote layout.
Puppeteer / PlaywrightHeadless Chrome. Excellent CSS fidelity but requires a running Chrome process — heavy for a solo dev stack and adds a Node.js dependency.
External service (DocRaptor, etc.)Sends quote content to a US SaaS — GDPR concern, adds a subprocessor, unnecessary cost.

WeasyPrint runs inside a Celery worker (the default queue). PDF generation is triggered when a quote is sent or explicitly requested. The resulting PDF is uploaded to bf-files/{org_id}/quotes/{quote_id}/quote-v{rev}.pdf and the URL is stored on the Quote model.

WeasyPrint system dependencies: requires libpango, libcairo, libgdk-pixbuf on the server. Add these to your Dockerfile and server setup script from day one — they're the most common source of "works locally, fails in production" issues with WeasyPrint.

CDN, DNS, SSL — Cloudflare + Caddy

Cloudflare (DNS + CDN + DDoS)

Put your domain on Cloudflare from day one. Even on the free plan you get: global DNS (fast propagation), DDoS protection, SSL termination (or pass-through), basic WAF, analytics. Do not proxy customer file uploads through Cloudflare — 200MB STEP files will hit Cloudflare's 100MB request size limit on the free/pro plan. Use DNS Only records (grey cloud) for the upload endpoint; use proxied records (orange cloud) for the app and API.

PlanPriceWhen to upgrade
Free€0Pilot — more than adequate
Pro$25/moSaaS — adds WAF rules, better analytics, priority support, 200MB upload limit (still grey-cloud uploads to bypass anyway)

Caddy (reverse proxy + automatic HTTPS)

Run Caddy on each app server as the reverse proxy in front of uvicorn. Caddy automatically provisions and renews Let's Encrypt certificates — zero SSL management overhead for a solo dev. Caddyfile example:

app.bidfactory.app {
    reverse_proxy localhost:8000
}

That's it. Caddy handles HTTPS, HTTP→HTTPS redirect, certificate renewal, and HTTP/2.

Monitoring & Observability

A solo dev needs three things: know when something breaks, know what broke, and know how the system is performing under load. Three tools cover this with minimal overhead.

Sentry — error tracking + performance

Sentry SDK for Python (FastAPI) + JavaScript (React). Captures unhandled exceptions with full stack traces, request context, and user info. The FastAPI integration is two lines of code. Use Sentry's EU data region (errors contain stack traces which may include user IDs / quote data fragments — keep in EU).

Betterstack — logs + uptime

Betterstack (formerly Logtail) ingests structured logs from the FastAPI app and Celery workers via a log drain or the Python logging handler. Also provides uptime monitoring with status page. EU servers available (Frankfurt). Start using this at the SaaS stage — pilot debugging can be done with journalctl / Docker logs directly.

PlanPriceWhen
——Pilot — use journalctl -u bid-factory and Sentry
Starter$25/monthSaaS — structured logs, 7-day retention, uptime checks, status page for customers

Prometheus + Grafana Cloud — metrics

FastAPI exposes a /metrics endpoint via prometheus-fastapi-instrumentator. Scrape with Prometheus; visualise in Grafana Cloud (free tier: 10k active metrics, 50GB logs). Key dashboards to build: request latency p50/p95/p99, Celery queue depth per queue, PostgreSQL query times, geometry job duration histogram. Start this at the SaaS stage.

The most important alert to set up on day one: Celery geometry queue depth > 10 for more than 5 minutes. This means jobs are piling up — the geometry worker is overwhelmed or dead. Without this alert, a customer will wait 20 minutes for their STEP file to process and you won't know.

CI/CD — GitHub Actions + Kamal

GitHub Actions (test + build)

Two workflows: PR check (pytest, type check, extraction eval suite on fixture drawings) and deploy (triggered on merge to main). Keep test suites fast — the extraction eval suite with 10 fixture drawings should complete in under 3 minutes.

Free tier: 2,000 minutes/month for private repos. At ~5 min/run, that's 400 runs/month — more than enough for solo development. Upgrade to Team ($4/month) only if you exceed the limit.

Kamal (deployment)

Kamal is a deployment tool (used by Basecamp/Rails) that deploys Docker containers to any VPS via SSH — no Kubernetes, no Heroku, no platform lock-in. It handles zero-downtime deploys (rolling restart with healthchecks), secrets injection, and rollback. A config/deploy.yml file defines servers + image + env. One command: kamal deploy.

service: bid-factory
image: ghcr.io/you/bid-factory
servers:
  web: [app-01.hetzner.ip, app-02.hetzner.ip]
  worker: {hosts: [worker-01.hetzner.ip], cmd: celery -A app.tasks worker -Q geometry}
proxy:
  ssl: true
  host: app.bidfactory.app

GitHub Actions calls kamal deploy after tests pass. The whole CD pipeline is under 10 minutes including Docker build, push to GitHub Container Registry, and rolling deploy to Hetzner.

Environment strategy: Three environments from day one — local (Docker Compose), staging (single Hetzner CX22, mirrors prod), production. Every merge to main deploys to staging automatically; production deploy requires a manual trigger (or a tagged release). This prevents the pilot customer seeing broken code.

Secrets Management — Infisical (self-hosted) ✓ DECIDED

API keys (Anthropic, Mailgun, Clerk, Hetzner Object Storage) must not be hardcoded or committed to the repo. Infisical self-hosted on Hetzner is the chosen solution — fully EU, no third-party subprocessor, open source, free.

PlanPriceWhat it gives you
Free (Developer)€0Unlimited secrets, 3 projects, CLI, GitHub Actions integration. Sufficient for pilot.
Team$10/monthAudit logs, team access, service account tokens. Needed when more than one person has access.

Infisical runs as a Docker container on a small Hetzner CX22 (€4/month) or as a service on the app server. It exposes a CLI and GitHub Actions integration identical to Doppler. Inject secrets at deploy time via infisical run -- kamal deploy. No customer data ever touches Infisical — only your own infrastructure credentials.

Add Infisical to the Docker Compose local dev stack so secrets work identically in development and production. The Infisical instance itself should be set up as part of the pre-build infrastructure checklist, before any other service is configured.

Payments — Stripe (v1.x)

Not needed for v1. The build spec decision is PO-only checkout for v1; card checkout is v1.x. When card checkout ships:

  • Provider: Stripe. Best-in-class API, EU data residency option, GDPR DPA available, strong German-market presence
  • Use Stripe Connect if you ever want marketplace-style payments (shops getting paid by their customers through BF); standard Stripe for direct billing
  • For v1.x, only the buyer checkout (buyer pays the shop via BF) is in scope — not the shop paying BF's subscription (that's separate billing infrastructure)
  • Stripe Elements (pre-built UI) avoids PCI scope on your servers — card data never touches your backend
