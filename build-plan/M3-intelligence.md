# M3 — Intelligence (Lens, Rules, Email Ingest & Threading)

**Spec:** [#milestones](../docs/spec/Bid-Factory-Build-Spec.html#milestones) (M3 row) · **Exit criteria (authoritative):** a fixture `.eml` → draft quote with prefilled parts; a fixture drawing → extractions overlay; the Demo C rule library works end-to-end; a reply round-trips and threads correctly; the new-quote notification card renders a triage brief with the correct signals.

**Goal.** Make the product *intelligent* — the three soft subsystems that read intent from documents and email, and the rules layer that turns what they find into assignable review work. Lens (AI extraction) reads prints/PDFs/email bodies into `ExtractionFinding`s; the rules engine evaluates a serialized query AST over a component's analyzed data into review items; email ingest turns an inbound RFQ into a draft quote; two-way threading lets the estimator reply from their own mailbox. Two T1 AI features ship here (Triage Brief, Rule Auto-Suggestion). **AI output is suggestions only** — purple AI-Governor, 55% opacity, explicit Accept, never auto-fed into Kalk, never hallucinated — and that is baked into every acceptance check.

**Golden-thread role.** M3 **replaces the thread's intake mock**: the golden-thread quote no longer originates from a direct-create call but from a **real ingested RFQ `.eml` + Lens prefill** (carried by `M3.3` ingest + `M3.4` bulk-create). The M1 golden-thread integration test must stay green — the thread can only get *more real*, never break.

**This milestone follows the M1 worked example** for block template and citation density exactly.

**AI test plan (two tracks).** Lens output is *probabilistic*, so M3 is tested on two tracks (see `README.md` → "Testing the two kinds of block"): the **deterministic core** — `ExtractionFinding` schema/persistence, the never-hallucinate *guard logic*, the rules AST evaluator, review-item lifecycle, email parsing — gets **exact unit tests that gate every PR** and **mocks the model**; the **probabilistic extraction quality** is scored by the **eval harness (M3.11)** — precision/recall/F1 per field category vs the spec targets (classification ≈95%, recall ≈65%, precision ≈85%), at temperature 0 + pinned model + versioned prompts, **threshold/regression-gated, never exact-match**.

**Sequence:** `M3.1 → M3.2` (Lens pipeline then its panel) ⟂ with `M3.6 → M3.7 → M3.8` (rules schema → evaluator → review-item lifecycle); `M3.3 → M3.4` (ingest → bulk-create) depend on M3.1 and **carry the golden-thread swap**; `M3.5` (threading) is orthogonal after M3.3; `M3.9` (Triage Brief) chains after M3.3; `M3.10` (Rule Auto-Suggestion) depends on the rules engine (M3.8). The two AI features sit last because they consume the pipelines beneath them.

### M3.1 — Lens extraction pipeline + `ExtractionFinding` schema/persistence   `[L]`
- **Vertical slice:** a fixture drawing runs through the document-extraction pass and persists structured `ExtractionFinding`s — value + units + bbox + confidence + status — with the never-hallucinate guard enforced.
- **Scope (in):** the `ExtractionFinding` table/schema (`category` ∈ quote_setup|requirements|features|dimensions|regions; `type`; `raw_text`/`value`/`normalized_value`/`units` mm-default; `tolerance{kind,upper,lower}`; `role`; `bbox`; `confidence`; `status` suggested|accepted|rejected|edited; `gdt{symbol(ISO GPS),datum_refs,material_condition}`); the **two-pass** extractor (quote-setup pass whole-file on upload; requirements pass per "print"-classified page, first 10 pages); per-task vision-LLM routing via the configurable provider; per-finding confidence; the **never-hallucinate guard** (a value absent from the print is never emitted); the **EU/GDPR routing guarantee** (export-control/dual-use flagged file never leaves the DPA region); async via Celery.
- **Scope (out):** the Found-in-Files panel UI + click-to-fill (→ M3.2); email-body parse (→ M3.3); BOM-table → BomNode tree building (→ M4, needs assemblies); 3D-PDF/PMI annotation extraction (→ geometry, M4); **Lens pipeline 5** — CAD-metadata material/quote-inclusion classification ([#lens-cad-classify](../docs/spec/Bid-Factory-Build-Spec.html#lens-cad-classify)) — lands with **M4.10b** (needs `decompose_bom` metadata; reuses this block's `ExtractionFinding` infra with the new `material`/`quote_inclusion` finding types); the file-processing pre-stages (virus scan / unlock / PDF-as-ZIP unpack / OCR) land with the viewer file pipeline (→ M2) — this block consumes a text-extractable PDF.
- **Depends on:** M1.2 (file storage), M2 file-processing pre-stages (OCR/unpack — *may stub a digital PDF until M2 lands*)
- **Implements (spec):** [#lens-engine](../docs/spec/Bid-Factory-Build-Spec.html#lens-engine), [#lens-finding](../docs/spec/Bid-Factory-Build-Spec.html#lens-finding)

### M3.7 — Rules AST evaluator (gated on interrogation state)   `[M]`

### M3.10 — Rule Auto-Suggestion (AI Feature 2, human-gated)   `[M]`
- **Vertical slice:** when an estimator manually adds the same operation to 3+ similar parts, a non-blocking chip suggests turning it into a rule and opens the pre-seeded Create Rule dialog — but AI never creates the rule.
- **Scope (in):** `added_manually BOOL` on `OperationInstance` (set on direct estimator add, cleared when added by a rule resolution); the **pattern-detection DB aggregate** (same operation manually added to 3+ parts in the same process family + material class in the last 90 days); a Claude call that **only** writes the human-readable suggestion sentence + pre-seeds the Create Rule dialog (signal name, operation, likely condition); the **non-blocking suggestion chip** in the operation drawer + the nightly batch surfacing it on the dashboard suggested-actions strip via the existing `SuggestedAction` mechanism; gated by `org_ai_settings` (`rule_suggest_enabled`).
