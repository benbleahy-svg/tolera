# M6 — Differentiators + Pilot Hardening

**Spec:** [#milestones](../docs/spec/Bid-Factory-Build-Spec.html#milestones) (M6 row, demos 22–26) · **Exit criteria (authoritative):** **pilot checklist green**; **all 14 demo narratives replayable on fixtures/seeds**; the NL-search query **"lost titanium 5-axis quotes over €10k"** returns the correct filtered results; the MCP **`get_open_quotes` + `get_triage_brief`** tools return correct JSON against seeded data.

**Goal.** The golden thread is **already fully real** at the end of M5 (real intake → real dims → real costing/pricing → real PDF/email/portal/order). M6 builds the **four v1 differentiators** *around* that spine — the work-queue **Dashboard**, the **Vendor RFQ Portal**, the DACH **adapters** (Würth, HubSpot, ERP-push stub) — then **hardens the pilot**: GDPR/export-control pack, a perf pass on large BOMs, and the AI surface that ships in v1 (NL Search BETA + the Tier-3 MCP server). The milestone **ends with a full acceptance-script replay** of all 14 demo narratives across the seeded demo tenants — that replay is itself the final block.

**This file follows M1's block template and citation density exactly.** (M1 is the worked example; M6 is the last milestone.)

**Golden-thread role.** M6 does **not** replace a thread segment — by M5 there are no mocks left. Two of its blocks *plug into* the thread (Vendor Quotes write the thread's Outside-Services cost; the work-queue surfaces the thread's quote), and the closing block **re-runs the thread's golden integration test inside the 14-demo replay**. Every M6 block must leave the thread's CI test green.

**Sequence:** `M6.1 ⟂` (dashboard, off the existing list/quote data) leads. The **Vendor RFQ chain is sequential**: `M6.2 → M6.3 → M6.4 → M6.5 → M6.6` (portal infra → vendor library → batch-send → outbound email → quotes-panel-apply). The **adapters are orthogonal**: `M6.7 ⟂` (Würth) and `M6.8 ⟂` (HubSpot/ERP) branch any time after M5's REST/event bus exists. `M6.9 ⟂` (hardening) runs in parallel. `M6.10` is **last** — it depends on the full product being present (it replays all 14 demos) and on the seeded demo tenants from M1.12/M5.

> **Adapter posture (decided, applies to M6.7/M6.8).** Every external connector is **mock-first**: build against a documented fixture response so real credentials slot in **without code changes** (`DECISIONS.md` — Würth API access; Infrastructure-Audit adapter pattern; `DACH-DELTA-LAYER §6`). Do **not** block M6 on procurement.

### M6.1 — Dashboard work-queue redesign (urgency formula + reason chips + recents + KPI row)   `[L]`  ⟂
- **Vertical slice:** the landing page becomes a single merged, role-aware, prioritized **work queue** — each row shows *why it surfaced*, ordered by a **deterministic, explainable urgency score** — with a recently-opened strip and a manager KPI row; the classic three-panel Workflows table survives as a saved view.
- **Scope (in):** the merged queue across **quotes needing my action · tasks assigned to me · review items assigned to me · vendor RFQs awaiting send/ingest · @mentions**; the **urgency score** `w1·days_to_due⁻¹ + w2·quote_value_band + w3·unresolved_count + w4·flags(expedite/VIP/export)` with **org-configurable weights** (Settings, sensible defaults shipped) and **explainability** (contributing factors on hover); per-row **reason chips**; the **Recently opened** strip (last 8 quotes/parts, thumbnail + status); the **KPI glance row** for managers (open quotes, due this week, win-rate 30d); retain global search, notifications feed, "View all tasks / review items". Vendor-RFQ queue rows depend on M6.2's entities — gate that source behind a feature flag until M6.2 lands, or branch and integrate.
- **Scope (out):** the classic reference dashboard table (kept as a saved "Workflows" view from M1.3 — not rebuilt); analytics tiles/charts (→ **M7**, deferred); the vendor follow-up suggested-action *generator* (→ M6.6, which produces the "no response" item the queue then displays).
- **Depends on:** M1.3 (saved-view + quotes list), M5 (orders/send so "needs my action" is real); ⟂ otherwise
- **Implements (spec):** [#newscope](../docs/spec/Bid-Factory-Build-Spec.html#newscope) (Dashboard redesign + urgency formula), [#dashboard](../docs/spec/Bid-Factory-Build-Spec.html#dashboard) (regions retained/replaced)

- **Acceptance criteria:** the queue merges all five source types for the signed-in user/role; reordering org weights re-sorts deterministically and the hover panel shows the per-factor contribution; the same seed yields a stable ordering (no time-of-render nondeterminism beyond `days_to_due`); a cross-org row is labelled and switches org on select; the "Workflows" saved view still renders the classic table.

### M6.2 — Vendor RFQ Portal — unauthenticated entrypoint + QuoteToken (vendor_rfq scope)   `[M]`
- **Vertical slice:** an unauthenticated vendor opens a **signed-token** portal page at `/vendor-rfq/:token`, sees the parts table for exactly its RFQ batch, fills the per-line response form, and submits — no account, no access to any other tenant data.
- **Scope (in):** the **separate unauthenticated React bundle** (no auth middleware) at `/vendor-rfq/:token`; the **unified `QuoteToken`** table with `scope ENUM(buyer_portal | vendor_share | vendor_rfq)` (one token model for all three external-access mechanisms — decided), signed-JWT verification scoped to one RFQ batch + one vendor; the portal **parts table** (part no/rev/description/process/qty breaks/estimator notes/thumbnail/file download), the **per-line response form** (unit price per qty break, lead time days, notes, **"Cannot quote this part"** for partial response) + quote-level valid-until + optional file attachment, **Submit**; **Download RFQ PDF**; tenant branding header; **portal never shows a hard "closed" state** (open after need-by; late submit allowed); usage instrumentation (open/submit/apply rate) from day one.
- **Scope (out):** the batch-send compose modal that *creates* the RFQ (→ M6.4); the outbound email (→ M6.5); the estimator-side Vendor Quotes panel + apply-to-costing (→ M6.6); email-reply ingest (→ M6.5).
- **Depends on:** M5 (ExternalShare/`QuoteToken` infra + buyer portal established there), M1.5 (line items the RFQ references)
- **Implements (spec):** [#vendor-rfq](../docs/spec/Bid-Factory-Build-Spec.html#vendor-rfq) (portal route, token, response form, late-response behaviour), [#collab](../docs/spec/Bid-Factory-Build-Spec.html#collab) (ExternalShare tokened-link infra reused)
- **Internals (provenance):** ../docs/spec/folded-subspecs/INTEGRATION-API-CONTRACT.md (external-access token + scoped delivery patterns)
- **KB:** [KB: internal-collaboration](https://help.paperlessparts.com/s/article/internal-collaboration)
- **Decisions:** ../docs/decisions/DECISIONS.md → log `OPEN:` if the vendor-RFQ JWT TTL / "Require 2FA for external share" applies to vendor scope is not already fixed by the M5 token decision — do not invent a TTL.
- **Acceptance criteria:** a valid token renders only its batch's parts; a tampered/expired token is rejected; a partial response (some lines "cannot quote") submits; a submission after the need-by date still succeeds (portal stays open); the vendor bundle cannot reach any tenant data beyond the RFQ scope.
- **Test plan (fixtures):** seed a `vendor_rfq`-scoped `QuoteToken` against a fixture RFQ batch; assert render-scope, signature-verification (valid/tampered/expired), partial + late submission persistence, and cross-scope denial.
- **Golden-thread role:** none (parallel feature); must not touch the thread's pricing path.

### M6.4 — Vendor RFQ batch-send modal (line checklist · ranked vendor selector · files/redacted toggles · blind multi-send)   `[L]`

- **Scope (in):** the two entry points → **same modal** (Quote Detail line multi-select toolbar "Send Vendor RFQ"; Part Estimating "Get Vendor Quote" with current line pre-selected; add/remove lines in-modal); fields — **line-item checklist** (part no/thumbnail/process/qty breaks), **vendor multi-select filtered to matching process types** with **AI-suggested pre-check** (rank: most-recent-accepted → historical acceptance rate → process match → material match; **New** label for zero-history vendors), **need-by** date, **message**, **files** toggle per vendor (supports the M2 **redacted** copy); the **`VendorRFQ`** entity (`org_id`, `quote_id`, `line_item_ids[]`, `created_by`, `need_by_date`, `status ENUM(open|closed|…)`); on send, **one RFQ per vendor, BCC-isolated** (vendors cannot see each other), each carrying a `vendor_rfq`-scoped `QuoteToken`; the **Operation-level vs Part-level(Buy)** distinction recorded so responses map correctly (Buy mode: `LineItem.costing_mode ENUM(make|buy)` — flips the line to buy, response sets `outside_service_cost`); the "⏳ Awaiting N vendor response(s)" chip on Outside-Services + the soft warning on workflow-stage advance while RFQs are open.
- **Scope (out):** the email transport itself (→ M6.5); response ingest + apply (→ M6.6); the follow-up suggested-action generator (→ M6.6); full Buy-mode nesting interaction (→ owned by the M4 nesting block; here only the costing_mode flag + cost field).

- **Implements (spec):** [#vendor-rfq](../docs/spec/Bid-Factory-Build-Spec.html#vendor-rfq) (batch modal, vendor ranking, blind send, Buy mode, awaiting-chip + soft warning), [#collab](../docs/spec/Bid-Factory-Build-Spec.html#collab) (blind multi-quote / per-recipient file scoping reused)

### M6.6 — Vendor Quotes panel + one-click apply-to-costing + follow-up suggested action   `[M]`
- **Vertical slice:** all vendor responses for a line item render side-by-side on the Part Estimating Outside-Services section and Quote Detail; the estimator **applies one** with a click — writing the vendor price into the Outside-Services cost (the thread's real outside cost) — and an unanswered RFQ produces a human-authorized follow-up.
- **Scope (in):** the **Vendor Quotes panel** (columns: Vendor + contact · **price per qty break** · lead time per qty break · valid-until · notes · **Source** = Portal | Email(AI-extracted) · **Cannot-quote** flag · **Apply**); **one-click Apply** writes the vendor price to the line's `outside_service_cost` (Operation-level → that outside step; Part-level/Buy → the buy line), with unselected responses **archived** to the vendor's RFQ History; the **late-response** in-app alert; the **need-by-passed → Dashboard suggested action** "Follow up with [Vendor] on RFQ #X" gated behind **Authorize Follow-up** (human-in-the-loop; the queue from M6.1 displays it); **display-only history hints** ("typical anodize cost X–Y €") once data accumulates.
- **Scope (out):** writing history back to ERP (never — BF-only data); auto-applying any AI-extracted value (forbidden — explicit apply only); the analytics roll-up of vendor spend (→ M7).
- **Depends on:** M6.5 (responses exist), M6.4 (RFQ + Buy-mode), M1.7 (Outside-Services cost cell + calc-vs-override the apply writes into), M6.1 (work queue that shows the follow-up action)
- **Implements (spec):** [#vendor-rfq](../docs/spec/Bid-Factory-Build-Spec.html#vendor-rfq) (Vendor Quotes panel, Apply→costing, archive-to-history, late alert, authorize-follow-up, history hints)
- **Internals (provenance):** ../docs/spec/folded-subspecs/PRICING-ENGINE-SPEC.md (Outside-Services cost category the applied price lands in; calc-vs-override persistence)
- **KB:** [KB: adding-a-supplier-material](https://help.paperlessparts.com/s/article/adding-a-supplier-material)
- **Decisions:** ../docs/decisions/DECISIONS.md → *Lens never auto-feeds costing* (Apply is the explicit accept); *Calc-vs-override* (`COALESCE(manual_*, calc_*)` — an applied vendor price is the manual outside cost, persisted alongside any calc)
- **Acceptance criteria:** multiple responses for one line render side-by-side with the right Source tag; **Apply** writes the chosen price into the Outside-Services cost and the roll-up reflects it; unselected responses move to RFQ History and stay visible on the vendor detail; no AI-extracted value is applied without the click; a need-by-passed RFQ yields a suggested action that only sends after Authorize.
- **Test plan (fixtures):** seed two vendor responses (one portal, one email-extracted) for an outside operation; assert Apply updates `outside_service_cost` and the cost roll-up; assert archive-to-history; assert the follow-up action requires authorization before send.
- **Golden-thread role:** **plugs into the thread** — if the thread's part has an outside process, applying a vendor quote sets its real Outside-Services cost; the thread's golden figure must still reconcile (vendor-cost path is additive, not a regression).
