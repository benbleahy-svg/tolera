Claude Code Workflow Playbook

How a 2–3 person team + Claude Code turns 78 spec'd blocks into a shipped DACH quoting platform — what to run, when to run it, when to open a second terminal, and how to hand work off. Built around your actual plan (one block = one session = one PR), your installed Matt Pocock skills, and a layered review stack that reads the diff when humans can't.

Stack: Python/FastAPI + Vite front-end 78 blocks · M0→M6 2–3 devs + Claude Code Context is the scarce resource

The one-paragraph answer

Run one Claude per block, one block per session, one PR — that is the spine, and it's already baked into your plan. Don't reach for an orchestrator-spawns-builders pattern: your blocks share a schema, migrations and a golden thread, so N Claudes writing in parallel creates merge hell. Instead, get parallelism for free in two safer ways: (1) sub-agents inside one session for read-only fan-out (explore, research, review) and (2) git worktrees + a second Claude only on the blocks your plan marks orthogonal (⟂). Wrap every block in a tight loop — grill → TDD build → diagnose → local review → fixtures green → PR → bot review → you accept → merge — and you stay the human gate on exactly the thing you care about: a working module.

  • Multi-Clauding & worktrees: yes — but as a scalpel for ⟂ blocks, not a default. The /rename + /colour terminal trick is genuinely worth it.
  • Loops: five of them, nested. The inner TDD loop does the heavy lifting; an autonomous CI loop comes later (M6), not now.
  • Install now: Matt Pocock skills + /setup-matt-pocock-skills, CodeRabbit CLI (free), git-guardrails hooks, REVIEW.md. Python toolchain via uv; bun only touches the front-end.
  • Team (2–3): claim each block as a GitHub issue (assignment = the lock), let CodeRabbit + Claude read the diff, and hand off with /handoff + the PR description. CODEOWNERS keeps money/schema/auth changes gated to the lead.

4One Claude or many? The honest verdict

“Multi-Clauding” is real and the context-switching argument is right — but it only pays when tasks don't touch the same files. Your plan literally marks those with ⟂. Here's the decision rule.

① Default — the spine

1 Claude · 1 block · 1 PR.

Use for all of M0, all of M1, and any block on the dependency chain. The schema, migrations, auth and golden thread are shared state — serialise them. This is ~70% of the build.

always start here

② Fan-out — inside one session

1 Claude · N read-only sub-agents.

For research, exploration, and review — “survey how PP handles X across the KB,” “review this diff from 3 angles.” Sub-agents read; they don't write. Zero merge risk; saves your main context.

explore · review · research

③ Parallel — worktrees

N worktrees · N Claudes · N branches.

Only on ⟂ orthogonal blocks: M2 viewers ∥ M3 extraction; settings sub-trees; file-storage ∥ saved-views. Each in its own worktree + terminal.

⟂ blocks only

How to actually run worktrees

# Claude makes the isolated dir + branch for you claude --worktree m2-pdf-viewer claude --worktree m3-lens-extract # → .claude/worktrees/<name>/ on branch worktree-<name>

Tell your terminals apart (the trick you mentioned — it works): in each session run /rename m2-viewer and /colour blue, the other /rename m3-lens + /colour purple. No more “which Claude is mid-edit?”.

Merge discipline: one branch at a time → run the full suite → then the next. Conflicts? /resolving-merge-conflicts.

⚠ The merge-hell trap — avoid this

Do not point two Claudes at blocks that share files. The classic failure on a schema-heavy project:

  • Two branches both edit DB-SCHEMA / add Alembic migrations → revision conflicts, broken history.
  • Both edit the shared pricing roll-up or the domain model → silent logic clobber.
  • “Hold on, the other Claude just renamed that module” → wasted session.

Rule: before opening a 2nd worktree, list the files each block touches. Overlap → sequential. Disjoint → parallel.

TWorking as a 2–3 person team

Your plan was written for one builder; this is the thin layer that makes it safe for a few. Three themes: claim before you build, let the bots read the diff, and hand off in writing — never leave state trapped in one person's chat.

claim  No collisions

Each block is a GitHub issue. Assigning it to yourself is the lock. Take the lowest-numbered block whose deps are merged — two people never grab the same one.

gate  CODEOWNERS

Changes to models/, migrations/, pricing/, auth/ auto-require the lead's approval. The irreversible stuff stays human-gated.

handoff  In writing

/handoff compacts a session → commit it to the branch / PR. With CLAUDE.md as the shared brain, a teammate (or a fresh Claude) resumes cold.

Two people, two tracks

Run in parallel only on ⟂ blocks (M2 viewers ∥ M3 extraction is the first window). Each in its own worktree + terminal (/rename, /colour).

One rule above all: only one person touches schema/migrations at a time — serialise models/, migrations/, pricing/. Merge one branch at a time, test between.

Onboard a teammate in ~15 min

Clone → cp .env.example .env (fill from the vault) → uv sync → pre-commit install → Matt Pocock skills + CodeRabbit CLI. Then read CLAUDE.md → this playbook → CONTRIBUTING.md. Shared .claude/settings.json ships in the repo.

5The five loops (nested, fastest on the inside)

“Are loops a good thing?” — yes, and you already run more than you think. The art is keeping the fast loops fast and the expensive ones rare. Inner loops run hundreds of times a day; the outer ones a few times a milestone.

seconds–minutes · constant

Tool: /tdd red→green→refactor
Exit: fixture assertion green

② Bug — Diagnose

minutes · as needed

Trigger: a test/behaviour breaks
Tool: /diagnosing-bugs
Exit: root cause + regression test

③ Review — pre-PR

~once per block

Trigger: block looks done
Tool: coderabbit + /code-review + @claude review
Exit: no 🔴, you accept

④ Architecture

every few days

Trigger: entropy creeping in
Tool: /improve-codebase-architecture
Exit: ball-of-mud risks logged/fixed

⑤ Golden thread

every milestone

Trigger: milestone exit
Tool: end-to-end fixture in CI
Exit: thread still green, one mock made real

M6+ · optional

The “RoboBun” pattern: a GitHub Action where @claude reads an issue → reproduces → writes a test/fix → opens a PR.

The one thing the bots can't do for you. AI reviewers catch bugs, leaks and rule violations well — but they can miss a value that's plausible but wrong for your domain (a misread tax rule, a subtly wrong pricing rounding). That's why the demo/fixture is the real acceptance oracle and a human owns money/tax/schema sign-off. Lean hard on tests + fixtures + types — they're your team's actual safety net, not eyeballing the diff.
